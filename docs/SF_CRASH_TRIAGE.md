# 崩溃现场采集与复现流程（Saturation Firepower DP / v160.5 主线）

本文件给出「服务端多人频繁崩溃」和「建造 DP 方块时新玩家进服立刻崩溃」两类问题的现场采集步骤。
目的：让每一次崩溃都留下**可定位到源码行**的证据，而不是靠猜。

## 0. 先确认版本组合（每次测试都要记录）

| 项目 | 取值 |
|---|---|
| 目标 Mindustry | **v160.5**（build 160 / revision 5，官方 server-release.jar SHA-256 `0BD327C6C3D551E7E8FDAB7B695517F809BAACCA3B1F5CB1C1A8DD74836620E0`） |
| 被转换 Mod | Saturation Firepower **4.0.6**（release JAR SHA-256 `895B76BA8A6A4E5EEB358C583A70056BA2D808260694fb20b16031c553c07ba6`） |
| DP 产物 | 需记录 ZIP 文件名 + SHA-256 + 生成它的 `report.json`/`runtime-mapping.json` |
| 服务端 | 官方 v160.5 服务端 **或** MindustryX（B495/B497…），务必写清 |
| 客户端 | 官方桌面 v160.x **或** MindustryX，务必写清；多人测试时所有客户端版本要一致 |

> 版本不一致本身就会造成"进服即崩"，因此每次复现都必须逐项对齐。

## 1. 崩溃报告在哪里（官方客户端/服务端都会自动写）

Mindustry 的崩溃处理器在崩溃时自动落盘（源码依据：`mindustry/net/CrashHandler.java:97-101`，
`mindustry/Vars.java:459`）：

```text
%APPDATA%\Mindustry\crashes\crash-report-<MM_dd_yyyy_HH_mm_ss>.txt   # 每次崩溃一份完整堆栈
%APPDATA%\Mindustry\last_log.txt                                     # 最近一次完整会话日志
```

- MindustryX / 自建启动器若改了数据目录，就在该目录下找 `crashes\` 与 `last_log.txt`。
- 崩溃弹窗本身也有复制按钮，可复制同一份堆栈文本；能复制就一并保存。
- 服务端同样有 `crash-report-*.txt`（服务端进程崩溃时）。

## 2. 采集清单（一次复现 = 一个文件夹）

建议每次测试新建 `crash-<日期>-<序号>\`，里面放：

1. `client-*/crash-report-*.txt`：**每个崩溃客户端**的崩溃报告（最重要）。
2. `client-*/last_log.txt`：崩溃前后完整日志。
3. `server/crash-report-*.txt`、`server/last_log.txt`：服务端侧文件。
4. `versions.txt`：服务端/客户端版本、MindustryX 版本、DP 文件名与 SHA-256、Mod 版本。
5. `map.msav`：出问题的地图存档（复现用的最小地图）。
6. `dp/`：正在使用的 DP 目录或 ZIP（含 `report.json`、`runtime-mapping.json`）。
7. `timeline.txt`：几点几分谁做了什么（例：`20:31 玩家B放置 dp-xxx 炮塔 → 20:31:20 玩家C加入 → 20:31:21 玩家C崩溃`）。

## 3. 问题一的复现（服务端多人频繁崩溃）

1. 服务端只装这一份 DP（不要与其他 DP/Mod 混装），客户端同样只装这一份。
2. 起服并让 2–4 个客户端进入同一张地图。
3. 按覆盖面依次操作，每做完一组记录一次时间戳：
   - 放置并完成建造：运输、电力、存储、工厂、钻头、炮塔各一；
   - 让工厂实际生产一次、炮塔实际开火一次（含换弹药种类）；
   - 生成/控制单位，触发武器、Ability、死亡效果；
   - 拆除方块、覆盖建造、被摧毁；
   - 保存地图并重新加载。
4. **谁崩了就把谁的 `crashes\*.txt` 收进来**，并记录崩前最后一个操作。

> 目标：先拿到 3–5 份**不同**崩溃堆栈。相同堆栈重复出现即可停止采集。

## 4. 问题二的复现（建造中的 DP 方块 + 新玩家进服）

最小复现脚本：

1. 服务端与客户端 A 进入同一张测试地图。
2. 客户端 A 开始建造一个 **DP 新增方块**（炮塔/工厂优先），**在建造未完成时停下**（保留建造进度，
   例如用低速建造单位/不提供足量物品，使方块处于 `ConstructBlock` 建造中状态）。
3. 保持该方块处于建造中，客户端 B **此时加入服务器**。
4. 记录客户端 B 是否立刻崩溃，以及 A 的建造进度是否中断。
5. 变体（用于区分根因，逐条单独测）：
   - a) 建造中的方块换成**原版方块**（对照：若原版不崩，则问题在 DP 方块本身）；
   - b) 换成**已建造完成**的同一个 DP 方块，再让 B 进服（对照：若完成态不崩，则问题在建造中状态）；
   - c) B 换成**官方客户端**、A 用 MindustryX（或反之），确认是否只在混用时崩；
   - d) 服务端重启后再让 B 进服，观察是否与"服务端热状态"有关。
6. 每组变体都收 `crash-report`，并写明属于 a/b/c/d 哪一种。

## 5. 采集完后怎么给我

把整个 `crash-<日期>-<序号>\` 目录的路径告诉我（或压缩后放到一个我能读到的目录）。
我会按堆栈直接定位到 v160.5 源码行与 DP 产物中的具体声明，而不是泛泛猜测。
